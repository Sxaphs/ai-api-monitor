# API 监测台 · 三方向共同设计 Spec

## 本质需求

这是运营方每天早会使用的竞品/上游监测台，不是数据大屏。用户需要先看到待核对预警，再判断价格、功能和营销变动，最后能一键回到原始证据。视觉必须服务“扫读—核对—追溯”，不能为了炫技牺牲密度。

## 受众与场景

- 受众：AI API 中转站运营、产品、采购/上游管理人员。
- 核心场景：每天北京时间 08:00 后查看前一日 08:00 至当日 08:00 的窗口；白天桌面为主，手机可临时核查。
- 情感基调：可靠、清晰、有秩序；预警明确但不制造恐慌。

## 三版共同内容（真实数据）

- 监测对象 26 个，A/B/C/D 分别为 8/8/4/6。
- 当前快照 25 条，有效变动 2 条。
- OpenRouter：Gemini Decision 1 公告（X 公告）。
- OpenRouter：MAI Transcribe 2 使用量公告（新功能分类）。
- 当前没有已入库价格变动；不能画虚构价格曲线或营销数字。
- 每条变动保留 `confirmed`、分组、检测时间和原文链接。

## 必备结构

1. 时间窗与监测覆盖范围。
2. 待核对/已确认状态与变动列表。
3. A/B/C/D 分组筛选、变动类型筛选。
4. 原文溯源入口。
5. 302.AI 类对象的“价格暂缺”说明样式（可用真实配置说明，不生成变动）。

## 输出与验证

- 六个候选：一页 `thumbs.html`，每格约 480×300。
- 三个完整版：各一个独立 HTML，桌面 1440×900，兼容 375×812；首屏和整页截图。
- 正文 ≥14px、标签 ≥12px，可点控件至少 44×44px；控制台零报错。
- 筛选和核对按钮在原型中真实可操作；OpenRouter logo 使用官方 SVG 的 base64 内嵌版。

## 既有 context

- 当前实现：深色导航 `#0f172a`、浅色背景 `#f8fafc`、正文 `#1f2937`、边线 `#e2e8f0`，表格优先。
- 新方案保留“证据优先”的产品逻辑，但不沿用当前通用表格皮肤。

## form 来自内容

- 08:00—08:00 的报告窗口形成时间轴/时间戳结构。
- `confirmed/pending/false_alarm` 形成核对状态，而非泛化彩色徽章。
- 每条变动的原始 URL 是界面核心操作，不是次要脚注。
